# Agent instructions — pizzeria

## Project overview

Pizzeria is an architectural sandbox demonstrating Domain-Driven Design end to end: an interactive simulation of a restaurant serving pizzas, where a Web GUI lets a user take on the roles of guests, a waiter, a chef, a host, and a manager, and observe the system's behaviour from the perspective of the whole pizzeria. The goal is to demonstrate the full process of domain discovery, strategic and tactical modelling, and then implementation using patterns such as Saga, Process Manager, CQRS, and CQS. The intended architecture (see `doc/09_architecture.md`) is a "Distributed Monolith": one Symfony codebase, four Bounded Contexts (Guest Service, Kitchen, Resource Management, Pizzeria Lifecycle), each deployed as several independent processes (HTTP, broker consumers, outbox relay), communicating only through published domain events — never a live cross-context query.

**Current stage: first implementation pass, one Bounded Context.** The DDD modelling process (steps 1–8) is reviewed and accepted; step 9 (Architecture) is drafted with two of its three Open Questions resolved (broker choice, idempotent consumption) and the third (HTTP/worker runtime) deliberately deferred until after this pass and real testing. `src/Kitchen/` is the first (and so far only) Bounded Context implemented, running under RoadRunner in Docker — see `doc/09_architecture.md` §6 and `adr/0001-message-broker-selection.md` for why. It uses **in-memory repositories, not a real database** (session decision) — every read model and repository lives in a plain PHP array scoped to the OS process that mutated it. This has a real, verified consequence: the HTTP worker pool, the jobs worker pool, and any `bin/console` invocation are each a **separate process** with their own empty state — only the jobs worker (which consumes `OrderSentToKitchen` over RabbitMQ) sees the state it creates. `src/Kitchen/UI/Console/*Command.php` and `OrderProgressController` will not see jobs-worker state until real shared persistence (Doctrine) replaces the in-memory repositories. Verification of this pass drove commands through the same RabbitMQ pipeline instead (see `JobDispatcher`'s internal-ops cases) specifically to stay in one process.
